# Implementation Roadmap

Each phase ships as its own set of commits. Design (Stitch) integration happens inside the relevant phase once assets are available — it does not block the architecture underneath it.

- [x] **Phase 1 — Foundation**: repo audit, monorepo architecture, dependencies, tooling, environment setup.
- [x] **Phase 2 — Database**: schema, migrations, RLS policies, seed data. Validated against a live local Supabase stack, not just parse-checked.
- [x] **Phase 3 — Auth & profiles**: sign up, sign in, password reset request, session-gated routing (`Stack.Protected`), a real 3-step onboarding wizard (musical taste, home neighborhoods, pace/crew/privacy — expanded from the original single username/interests screen once the real Stitch onboarding design landed, see `docs/onboarding.md`), profile view, logout, and account deletion (mobile → `apps/web` API → Auth Admin API). Verified end-to-end in a real browser against the live local stack, not just typechecked — see `docs/database-schema.md` for the bugs that surfaced only by doing that (an SSR crash, a `SecureStore` web gap, and a Zod datetime bug that caused a real infinite refetch loop). Not yet built: profile editing, avatar upload (needs Storage, not yet configured), email-confirmation deep linking.
- [x] **Phase 4 — Home feed**: posts, reactions, comments, following, pagination. Feed is a keyset-paginated RPC (`get_home_feed`) scoped to people you follow plus yourself; a "People to follow" strip (`get_suggested_people`) solves the empty-feed bootstrap problem until Discovery (Phase 9) exists. Verified end-to-end in a real browser — see `docs/feed.md`, including a real bug (not the already-documented NativeTabs web limitation) found while wiring up the comments screen: nesting a `Stack` inside a `NativeTabs.Trigger` doesn't deep-link reliably on web in Expo SDK 57, fixed by restructuring to a `Stack` that wraps the tab navigator instead. Not yet built: multi-reaction picker (schema supports it, UI doesn't yet), unfollow UI, ranked/non-recency feed ordering.
- [x] **Phase 5 — Real world**: vibes, places, events, check-ins. Explore tab is real now (places/events browse, city-scoped), with a place detail screen (check in, share a vibe, see who's here, upcoming events there) and an event detail screen (RSVP, check in, live attendee counts via `get_event_attendee_summary`). Event creation is a plain form (no place picker or rich date UI yet — deliberately deferred, see `docs/places-events.md`). Verified end-to-end in a real browser, including the check-in rate limit's error path and a real pre-existing bug found along the way: `app-tabs.web.tsx`'s floating web tab bar had no `bottom` anchor, so it sat invisibly over the top of every screen intercepting clicks — never triggered before because no earlier screen had interactive elements that high up. Fixed with an explicit `bottom: 0` and `pointerEvents: 'box-none'` so empty padding doesn't swallow clicks meant for the content under it.
- [x] **Phase 6 — Crews**: browse (public and private, both discoverable), create, join/request-to-join, admin approve/reject of pending requests, leave, member list, and a crew-scoped feed (posts with `crew_id` set and `visibility: 'crew'`, reusing Phase 4's post pipeline rather than a separate table). All DB-side from Phase 2 — this phase was entirely new UI plus one real PostgREST bug, fixed: an unqualified `profiles(...)` embed on `posts` is ambiguous because of the unused `saved_posts` many-to-many junction table, rejected with a 300 Multiple Choices; fixed with the FK-qualified `profiles!posts_author_id_fkey(...)` form. See `docs/crews.md`. Not yet built: ownership transfer (an owner can leave their own crew with no succession), crew avatar/cover image upload (needs Storage).
- [x] **Phase 7 — Retention loop**: XP, levels, streaks, badges, challenges. The ledger was schema-complete from Phase 2 with onboarding as its only writer; now a real trigger-driven engine awards XP for check-ins, posts, crew joins, event attendance, and reactions received, computes a real day-over-day streak, evaluates all 7 badges against real counts, and activates `challenges`/`challenge_participants` with real progress tracking and payout. Surfaced in UI on Home (streak/XP/level card), Profile (full stats, trophy case, activity ledger), and a new Crews-hub City Board leaderboard. See `docs/gamification.md`. Not yet built: `social`/`explorer`/`event` streak types (only `outside` is wired), challenge progress for `check_in`/`post_vibe`/`custom` types.
- [x] **Phase 8 — Notifications**: in-app + push. `notifications`/`notification_preferences` were schema-complete from Phase 2 with no writer; now a real trigger engine notifies on every real action this project has — follows, reactions, comments, crew join request/approval/rejection, challenge completion, level-ups, streak milestones, badges earned — plus the first time-based job in this project (`pg_cron`, event reminders) and real push delivery via `pg_net` straight to Expo's push API. Surfaced as a bell on Home with a live unread badge, a notification list, and a preferences screen. See `docs/notifications.md`. Not yet built: minting a real device push token needs an EAS project id this app doesn't have configured (needs a real Expo account — flagged, not started, same shape of gap as ticket payments).
- [x] **Phase 9 — Discovery**: search, trending, recommendations. Real fuzzy cross-entity search (people/places/events/crews, `pg_trgm`) replaces Explore's old client-side substring filter. Found and fixed a real bug along the way: the existing "Trending" place sort was silently a no-op, ordering by a static hand-seeded number instead of anything real — now sorts by the real recent-check-in count that was already being computed and just never read for this. "For You" recommendations (places/events/crews) rank by a real friend-graph signal (how many of the viewer's friends have been/are going/are already in) rather than fabricated interest-matching — considered and dropped, since onboarding doesn't currently collect real per-user interests (a separate pre-existing gap, flagged not fixed) and places' category vocabulary barely overlaps interests' anyway. Also added the public profile view (`/profile/[id]`) this and Phase 8's follow notifications both needed and neither had. See `docs/discovery.md`.
- [x] **Phase 10 — Sharing & deep links**: real share links (`expo-linking`'s `Linking.createURL`, no new native config needed) on all five entities with a detail screen — post, place, event, crew, profile — replacing the one pre-existing share call (plain text, no link) and giving it a real clipboard fallback for browsers without the Web Share API. Found and fixed a real bug along the way: `post/[id].tsx` never actually rendered the post, only its comments, which broke both a shared post link and Phase 8's follow/reaction/comment notification taps; fixed with a new `get_post_by_id` RPC (deliberately not `get_home_feed` with a filter added — that RPC's follow-graph scoping would make a link to a stranger's public post resolve to nothing) verified against Postgres directly across the full visibility matrix. Also fixed a second real bug surfaced only by live deep-link testing: all five detail screens' invalid-param redirect ran during render instead of in an effect, which is a real React warning, not just style — fixed everywhere via one shared `useRedirectIfInvalid` hook. See `docs/sharing.md`, including the real universal-link (`https://`) domain gap this doesn't attempt to close.
- [x] **Phase 11 — Moderation & safety**: `reports`/`blocks` were schema-complete from Phase 2 with zero consumers; `is_content_visible_to()` already checked blocks bidirectionally ("blocks always win") but nothing else did. Found and closed real gaps verified directly against Postgres before any client code existed: blocked people were still fully visible via `profiles` select, search, and suggested-people; `are_friends()`/the Phase 9 recommendation RPCs had no block-awareness (fixed once, at the shared `are_friends()` call site, since all of them call it rather than reimplementing it); blocking didn't unfollow and didn't prevent re-following; and `reactions_insert_self` — unlike `comments_insert_self` — had no visibility gate at all, letting anyone react to content, including private content, they couldn't even see. Shipped Block/Unblock/Report on profiles, Report on posts/comments/places/events/crews via one reusable component, and a blocked-users settings screen. Also found and fixed a real bug the new Block confirmation exposed: React Native Web's `Alert.alert` is a complete no-op, so every destructive confirmation in this app has silently done nothing on web since whichever phase introduced it — fixed for this phase's own new confirmation with a small cross-platform helper, flagged as a broader pre-existing gap rather than retrofitted everywhere. See `docs/moderation.md`. Not yet built: a moderator role or review queue for submitted reports — deliberately deferred to Phase 12 (Admin dashboard), which is what `reports`' own RLS (service-role-only resolution) was already designed around.
- [x] **Phase 12 — Admin dashboard**: the first real code in `apps/web` beyond account deletion — a Next.js admin area at `/admin` for reviewing the reports Phase 11 could only collect. There's no admin role in the database, so admins are a server-only `ADMIN_EMAILS` allowlist checked through one gate (`requireAdmin`) that runs in every privileged read and Server Action, not just the layout — confirmed necessary live, when a non-admin's request ran the reports page in parallel with a layout that was showing "Not authorized." Admins can triage reports (review, resolve, dismiss, reopen), soft-delete a reported post/comment/place/event/crew (the target is read back from the report row, never taken from the form), and suspend or reinstate users. Suspension is new (there was no ban mechanism at all): `profiles.suspended_at`/`suspended_reason`, enforced by `is_content_visible_to()` (a suspended user's content disappears for everyone, including themselves) and by a mobile root gate that shows the user the moderator's reason. Built to Next 16's Cache Components rules, following the guide shipped in `node_modules/next`: session reads behind `<Suspense>`, and `connection()` before the Supabase Auth round-trip. See `docs/admin-dashboard.md`. Not yet built: suspension doesn't block writes made directly against the API with a still-valid token (those rows are invisible but exist), left for Phase 14's security pass; and there's no admin CRUD for challenges, cities, or general place/event management.
- [x] **Phase 13 — Analytics**: `analytics_events` had existed since Phase 2 with no writer, and PostHog was named in the README and `.env.example` with no SDK or tracking call anywhere. Now one typed `track()` call sends every event to our own table (batched, through normal RLS) and, when `EXPO_PUBLIC_POSTHOG_API_KEY` is set, to PostHog. A shared catalog fixes every event name and its exact properties — deliberately free of personal content (no post or search text, route patterns instead of content ids) — covering launch, screen views, auth, onboarding, and every core action, each fired only after the server accepted the write. Because anyone can insert, the table now rejects malformed rows itself (name format, object-only and size-capped properties, server-stamped timestamps), verified as `anon`. Two real ordering bugs were designed out rather than found later: queued events must be flushed *before* sign-out (RLS rejects them after), so every sign-out path now goes through one helper; and sign-in must attribute its own event before the session listener runs. Users can opt out in Settings. A new `/admin/analytics` page shows active users, sessions, sign-ups, content counts (from the real tables, not client events), a new-user activation funnel, and top screens/actions via a `service_role`-only SQL function. Verified live in a browser, against a stand-in PostHog endpoint, and from a real iPhone. See `docs/analytics.md`. Not yet built: a real PostHog project (needs an account), insert rate limiting (Phase 14), event retention policy.
- [x] **App icon, splash, and name** (alongside Phase 13): the Expo starter's logo and blue splash replaced by a VYBE logomark generated from the design tokens, the app renamed VYBE with a `vybe://` scheme, and the web app's Next.js starter page/title/icon replaced. See `docs/design-system.md`.
- [ ] **Phase 14 — Testing, performance, security, accessibility hardening**.
- [ ] **Phase 15 — Production build & deployment**.

## Notes

- Stitch design assets have landed ("Afro-Electric Neon Obsidian" — see `docs/design-system.md`) and visual integration is underway, screen by screen, alongside the phases above rather than as a phase of its own. Auth screens, shared themed primitives, onboarding (`docs/onboarding.md`), and Home/Discover/Crews/Profile (`docs/gamification.md`) are done. Still ahead: Direct Chat, Squad Group Chat (no backend — new feature, not in this roadmap), app icon/splash. Some Stitch screens assume features well beyond the current backend (phone/WhatsApp OTP auth, real payments) — ported faithfully where the data is real, deliberately simplified or cut where it would otherwise be fake UI; each doc says which.
- Picking up Home/Discover/Crews/Profile pulled Phase 7 (retention loop) forward out of sequence, plus a Crews-hub leaderboard and real challenge progress that weren't explicitly phases of their own — the Stitch designs for those screens assumed that layer existed, so it was built rather than skinned around. Phase 8 (notifications) and Phase 9 (Discovery) then followed in their normal sequence — the "People Are Outside"/"busiest place" signals on Home and Discover were always a narrower, presence-specific thing, not a substitute for either.
- Each phase should leave `npm run typecheck` and `npm run lint` clean before moving to the next.
