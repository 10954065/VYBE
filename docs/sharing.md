# Sharing & deep links

## What was already real vs. what wasn't

Research before writing anything found: `app.json` declared `scheme: "mobile"` (since renamed to `"vybe"` with the app branding) but nothing used it; the only `Share.share()` call anywhere in the app was on the Explore event card, and it shared plain text (title + time + place), no link; there was no universal-link (`https://`) domain, no `associatedDomains`/`intentFilters`, and `apps/web` is still the untouched Next.js starter — none of that exists to build on. And one existing detail screen, `post/[id].tsx`, turned out not to show the post at all (see below) — a real problem for a phase whose whole point is "open this link and see the thing."

## Share links

`apps/mobile/src/lib/share-link.ts`'s `buildShareLink(entity, id)` wraps `expo-linking`'s `Linking.createURL()`, which already resolves correctly per platform with zero new config: `vybe://place/<id>` in a native build (from `app.json`'s `scheme`), `exp://host/--/place/<id>` in Expo Go, and the real `http://host:port/place/<id>` page URL on web — because the path matches the file-based route exactly (route groups like `(app)` never appear in the URL, confirmed against every `[id].tsx` screen). No new infrastructure, no new native config.

`apps/mobile/src/lib/use-share-link.ts`'s `useShareLink()` calls RN's `Share.share({ message, url })` and handles both outcomes a browser can produce: a browser that implements `navigator.share` (which includes Playwright's own Chromium, confirmed live — not "most browsers don't support this" as initially assumed) hands off to the OS/browser share sheet and resolves silently; a browser that doesn't (most real desktop browsers) rejects with "Share is not supported in this browser" — previously unhandled on the one existing `Share.share()` call, now caught and falls back to `expo-clipboard` (`setStringAsync`), surfaced as a transient "Link copied!" label via `apps/mobile/src/components/share-button.tsx`, the one component now used everywhere sharing is offered rather than five hand-rolled copies.

Share buttons were added to all five screens that have an `(app)/<entity>/[id]` detail route: place, event, crew, profile, and post. The event list card's pre-existing share call was pointed at the same hook/link instead of hand-built text, fixing its silent-rejection gap on web as a side effect.

## The real bug: `post/[id].tsx` didn't show the post

The post detail screen existed only to show comments — it had no `usePost`-equivalent hook and never rendered the post itself, relying entirely on the post still being visible in whatever screen you navigated from (the feed card above it, conceptually, even though the UI doesn't actually keep it visible). A shared link, or a follow/reaction/comment notification's tap target (both already routing here since Phase 8), would land on a wall of comments about something invisible.

Fixed with a new RPC, `get_post_by_id` (`20261010000000_get_post_by_id.sql`), and a new hook, `usePost`. It deliberately isn't `get_home_feed` with a filter bolted on: that RPC scopes to "people you follow plus yourself," which would make a shared link to a public post from a stranger resolve to nothing — exactly backwards for a feature whose job is to make a link work for whoever opens it. `get_post_by_id` drops the follow-graph filter and keeps everything else identical (same `security invoker` posture, same comment convention explaining why — the underlying `posts_select_visible` RLS policy, which calls `is_content_visible_to()`, still applies underneath regardless of which function queries the table, so dropping the filter can only widen which *already-visible* posts are reachable by id, never leak a hidden one).

Verified directly against Postgres before any client code existed: a one-way follower sees a stranger's `everyone`/`followers` posts but correctly not their `friends`/`only_me` posts; a true stranger (no follow relationship at all) sees only `everyone`; the author always sees their own posts regardless of visibility. All four cases matched expectations exactly.

`post/[id].tsx` now renders the real `PostCard` (reused as-is from the feed) above the comment list, wired to the same `useToggleReaction` mutation the feed uses — extended to also invalidate the new `["post", id]` cache key on settle, so liking from the detail screen and liking from the feed never drift. When RLS hides the post (or it was deleted), the screen shows "This post isn't available." instead of a blank wall of comments about nothing.

## Two bugs only live testing caught

**`usePost` returning `undefined` for "not found."** TanStack Query reserves a `queryFn` resolving to `undefined` for its own internal cache semantics and logs a dev warning if you return it yourself ("Query data cannot be undefined...") — caught live, the moment the followers-only-post-as-a-stranger case was exercised in the browser. `null` is the correct "there's nothing here, and that's a valid, cached answer" value; fixed and reconfirmed with zero console errors.

**All five `[id].tsx` screens' invalid-param redirect.** The established pattern across every detail screen — `if (!parsedParams.success) { router.replace('/home'); return null; }` called directly in the render body — produces a real React warning the instant it fires: "Cannot update a component (`NavigationContainerInner`) while rendering a different component." It never showed up before because nothing had fed one of these screens a syntactically-plausible-but-invalid id in a live session; a malformed deep link is exactly that. Since "an invalid deep-link target fails safely" is core to this phase rather than incidental, this was fixed everywhere at once with a small shared hook, `useRedirectIfInvalid`, that defers the `router.replace()` into a `useEffect` — same external behavior, no more warning. Reconfirmed live: `/place/not-a-real-uuid` still bounces straight to `/home`, now with zero console errors instead of one.

## What's still a gap, flagged not fixed

A real universal link (`https://vybe.app/place/...` opening the app directly, or falling back to a web page when the app isn't installed) needs a production domain, a hosted `apple-app-site-association` file, Android `assetlinks.json`, and `ios.associatedDomains`/`android.intentFilters` in `app.json` — none of which this project has, the same shape of gap as the EAS project id (Phase 8) and ticket payments. What's shipped works today for in-app navigation and for opening a link on a device that already has the app installed with the right scheme handler registered (verified architecturally via `Linking.createURL`'s documented per-platform output, and verified live for the web case, which is the one this dev environment can actually exercise end-to-end); the custom-scheme (`vybe://...`) dispatch from *outside* the app on a real iOS/Android device is not verifiable from this Windows + Playwright-web setup and is not claimed as tested here.

## Verified

Backend: `get_post_by_id`'s visibility matrix tested directly against live Postgres with three real test users across all four `posts.visibility` values. Client: every one of the five Share buttons exercised live in a real browser against the live local stack — the `navigator.share`-available path (silent success) and, by forcing `navigator.share` to `undefined`, the clipboard-fallback path ("Link copied!") both confirmed; cold navigation (not in-app `router.push`, a fresh `page.goto`) to `/place/:id`, `/event/:id`, `/crew/:id`, `/profile/:id`, and `/post/:id` all render correctly, including `post/:id` now showing real post content; liking a post from the detail screen confirmed to persist in the database and to use the same cache path as the feed; a stranger viewing another user's `everyone` post succeeds and their `followers` post correctly renders "This post isn't available."; an invalid id still redirects to `/home` (or `/explore` for crews), now without the React warning.
